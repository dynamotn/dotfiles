# dyai crew Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let one command run a task on any installed agent CLI (Claude, Codex,
Gemini, opencode, Copilot) in its own git worktree, have a different provider
review the result, and merge it back safely.

**Architecture:** A new sourced library `scripts/lib/dyai_crew.sh` drives each
agent CLI in headless mode. It never talks to a provider API, so every worker
keeps the skills, MCP servers and policy `dyai install` already gave its CLI.
The orchestrator holds no LLM: decomposition stays with the caller (a human,
or a lead agent that starts tasks with `dyai run --detach` and polls
`dyai tasks`). State is one append-only JSONL file per repository, guarded by
`flock`. Ideas borrowed from Bernstein (read 2026-10-26): worktree per task, a
completion file instead of trusting the exit code, log-tail rate-limit
detection with provider fallback, FIFO `--no-commit --no-ff` merge with abort
on conflict, cross-provider review.

**Tech Stack:** bash on dybatpho (`cli` module), git worktrees, `jq`, `yq`,
`flock`, `timeout` and `setsid` (coreutils, util-linux), bats.

**Spec:** none written. This plan is the design. Its decisions come from the
2026-10-26 conversation (ideas 1, 3, 4, 5 and the Bernstein source review),
revised the same day after a review that checked every agent CLI (see
"Verified agent facts").

## Global Constraints

- No new dependency. Only `jq`, `yq`, `flock`, `timeout`, `setsid`, `git` and
  dybatpho.
- Library functions are namespaced `dyai_crew::<verb>` and documented with
  `# @description`, `# @arg`, `# @stdout`, `# @exitcode`, like `dyai_hunk.sh`.
- Every changed script passes `dyshellint`. Exceptions carry
  `# dyshellint disable=<CODE> <reason>`.
- A prompt never travels as an argv element. Linux caps one argv string at
  128 KiB (`MAX_ARG_STRLEN`), and a review prompt carries a diff. The prompt
  goes into `<state_dir>/<id>.prompt.md` and reaches the agent on stdin, or as
  an attached file for opencode (see the table). Short fixed instructions may
  be argv. Nothing goes through `eval` or an unquoted expansion.
- Worktrees go in `<main checkout>/.worktrees/crew-<id>` on branch
  `crew/<id>`. Resolve the main checkout with
  `git rev-parse --path-format=absolute --git-common-dir`, so running from
  inside a worktree never nests one.
- Every registered worktree adds deny paths to Claude Code's Bash sandbox
  profile; past about 18 of them, every Bash call fails with `E2BIG` (seen on
  2026-10-26). So a task's worktree is removed as soon as it can hold nothing
  of value (Task 3), and `dyai drop` removes the rest (Task 5).
- Runtime state lives in `<main checkout>/.dyai/crew/`, added to the personal
  ignore with `dyai::git_exclude` + `dyai::exclude_add` (pattern `/.dyai/`).
- Task id: `$(date +%Y%m%d-%H%M%S)-<agent>-<4 hex digits>`, the suffix from
  `printf '%04x' $((RANDOM ^ $$ & 0xffff))`. Two runs in the same second on
  the same agent must not collide.
- Every agent process runs with env `DYAI_CREW=<id>`. Each hook dyai installs
  that would act on the user's desktop or context (`dyai-hunk`, the
  `global.hooks.stop`/`input` commands, the Claude SessionStart drift hook)
  returns at once when `DYAI_CREW` is set (Task 3).
- Never push, never touch `main`/`master` on merge, never `git branch -D`.
- No `CHANGELOG.md` (repository rule). Commit messages follow Conventional
  Commits with scope `dyai`, and carry no agent attribution trailer.

## Review Focus

1. A prompt larger than 128 KiB, holding quotes, newlines, `$(...)` or a
   leading `-`, reaches the agent byte for byte and runs nothing in the
   orchestrator. Test in Task 2.
2. Twenty `record` calls on the *same* id, started at once, each setting a
   different field: one line per call, every line parses, and the last state
   holds all twenty fields. Test in Task 2.
3. The agent exits 0 but writes no result file: the task is `failed`, not
   `done`. An agent that leaves branch `crew/<id>` is `failed` too. Test in
   Task 3.
4. A review verdict is parsed from each agent's real output envelope, not from
   the raw first line. Test in Task 4 with recorded envelopes.
5. `dyai merge` on a dirty working tree, or on `main`, refuses before
   touching anything; a fenced path at the repository root (`x.age`) stops
   it. Test in Task 5.
6. `dyai selftest` cannot pass on an agent whose deny rule is missing: the
   allow flag admits both probe calls, so only the deny rule can stop one.
   Test in Task 7.

### Task 2: Agent commands, output parsing and the task log

**Files:**
- Create: `scripts/lib/dyai_crew.sh`
- Create: `scripts/test/dyai_crew.bats`
- Create: `scripts/test/fixtures/crew/<agent>.<case>.out` (recorded output)

**Interfaces:**
- Produces:
  - `dyai_crew::cmd <agent> <mode> <prompt_file> <outvar> [last_file]`. Fills
    the array named `outvar` (nameref) with the command line, and sets
    `DYAI_CREW_STDIN` to the file the caller must redirect into stdin, or to
    `/dev/null`. `mode` is `rw` or `ro`. `last_file` is where codex writes its
    last message (`-o`). Adds the model flag when `model.<agent>` is set. Dies
    on an unknown agent.
  - `dyai_crew::text <agent> <out_file> [last_file]`. Prints the agent's final
    answer text from its output.
  - `dyai_crew::failure <agent> <out_file> <err_file>`. Prints
    `rate_limited`, `blocked` or nothing, from `tail -n 50` of the stderr file
    and from the agent's own error events.
  - `dyai_crew::state_dir`. Prints `<main checkout>/.dyai/crew`, creates it,
    and adds `/.dyai/` to the personal ignore.
  - `dyai_crew::record <id> <json>`. Under `flock` on `tasks.lock`, reads the
    task's last state, merges `json` over it plus `{id, ts}`, and appends the
    result as one line to `tasks.jsonl`. Reading inside the lock is what keeps
    two concurrent records from dropping each other's fields. Every line
    therefore holds the full state. When the line changes `status` and
    `hooks.on_status` is set, `record` runs the hook after the lock is
    released, with env `DYAI_TASK_ID` and `DYAI_STATUS`. A failing hook is
    logged with `dybatpho::warn` and never fails `record`.
  - `dyai_crew::get <id>`. Prints the last line for `id` as JSON. Exits 1
    when there is none.
  - `dyai_crew::list`. Prints the last line of every id, oldest first,
    as `id<TAB>status<TAB>agent<TAB>summary`. A `running` task whose
    recorded `pid` is gone, or now belongs to a process started at another
    time than the recorded `pid_start` (`ps -o lstart= -p <pid>`), is printed
    as `lost`. `list` never writes the log.

Command lines (from "Verified agent facts"). `P` is the prompt file. Every
line runs with cwd = the task worktree.

| agent | rw | ro differs by | stdin |
|---|---|---|---|
| claude | `claude -p --output-format stream-json --verbose --permission-mode acceptEdits --no-session-persistence` | `--permission-mode plan` | `P` |
| codex | `codex exec --sandbox workspace-write --ephemeral --json -o LAST -` | `--sandbox read-only` | `P` |
| gemini | `gemini --prompt "Follow the task given on stdin." --output-format stream-json --approval-mode auto_edit --skip-trust` | `--approval-mode plan` | `P` |
| opencode | `opencode run --format json -f P "Follow the attached task file."` | `--agent plan` | `/dev/null` |
| copilot | `copilot --silent --output-format json --allow-all-tools --deny-tool "shell(git push)"` | add `--deny-tool shell --deny-tool write` | `P` |

There is no `--strict-mcp-config`: it would drop every MCP server the worker
is meant to keep.

claude's `is_error: true` result and opencode's `type == "error"` event count

**Files:**

- Test: `scripts/test/dyai_hunk.bats`, `scripts/test/claude_settings.bats`

**Interfaces:**
- Consumes: Task 1 config keys, and `cmd`, `text`, `failure`, `state_dir`,
  `record` from Task 2.
- Produces: `dyai_crew::run <agent|auto> <prompt> [plan_file] [detach]`.
  Prints the task id. With a plan file, the plan is copied to
  `<state_dir>/<id>.plan.md`, recorded as `plan`, and appended to the prompt
  under `## Plan to follow`. Without `detach`, it waits and exits 0 when the
  task is `done`, 1 otherwise. With `detach`, it starts the attempt under
  `setsid` in the background, prints the id and returns 0 at once; the caller
  polls `dyai tasks`. Records the status (one of `running`, `done`, `failed`,
  `partial`, `rate_limited`, `blocked`, `timeout`) with
  `{agent, prompt, branch, worktree, base, pid, pid_start, summary}`. `base`
  is the commit the worktree was created from.

Behaviour:
- Warn when the current checkout has uncommitted changes: the worktree starts
  from `HEAD` and will not see them.
- Create the worktree from `HEAD` of the current checkout. If
  `hooks.post_create` is set, run it in the worktree with env `DYAI_TASK_ID`
  and `DYAI_WORKTREE`. When the hook fails, record `failed` with summary
  `post_create hook failed` and do not start the agent.
- Append a contract to the prompt: write `.dyai-result.json` at the worktree
  root as `{"status":"done|failed|partial","summary":"..."}`, stay on branch
  `crew/<id>`, and never push. Add `/.dyai-result.json` to the personal
  ignore.
- Run the array with stdin from `DYAI_CREW_STDIN`, env `DYAI_CREW=<id>`,
  stdout to `<state_dir>/<id>.out` and stderr to `<state_dir>/<id>.err`,
  under `setsid timeout --kill-after=30 <timeout>`. Record `pid` and
  `pid_start` of that process as `running`, then `wait` for it. On exit code
  124, kill the whole process group (`kill -- -<pid>`), so grandchildren the
  CLI started do not outlive the task.
- Agents may run shell commands in `rw` mode (see the facts table: codex,
  opencode and copilot can; claude can run what the settings allow), so the
  orchestrator does not assume it is the only committer. After the agent
  exits:
  1. `git -C <worktree> symbolic-ref --short HEAD` must still be `crew/<id>`.
     Otherwise record `failed` with summary `agent left branch crew/<id>`.
  2. Commit what is left: `git add -A && git commit -m "crew(<agent>): <summary>"`
     in the worktree, skipping the commit when nothing changed. Commits the
     agent made itself stay.
- The status comes from the result file. A missing or invalid file means
  `failed`. Exit code 124 means `timeout`. A non-zero exit where `failure`
  prints a value takes that value.
- Done needs evidence, not just the agent's claim. A `done` claim with
  `base..crew/<id>` empty after step 2 is recorded as `failed` with summary
  `claimed done without changes`.
- `rate_limited` and `blocked` write `<state_dir>/cooldown/<agent>`, holding
  the epoch until which the agent is skipped.
- `auto` walks `global.crew.fallback`. It skips agents that are not on `PATH`
  or are still cooling down, and moves on only after `rate_limited` or
  `blocked`. Each attempt is its own task id.
- Cleanup, because every worktree costs the user's sandbox profile: an
  attempt that ends `rate_limited`, `blocked` or `failed` with no commit on
  `base..crew/<id>` and a clean worktree is removed at once
  (`git worktree remove`, then `git branch -d crew/<id>`), and recorded with
  `worktree: null`. Anything with work in it is kept for `dyai drop`.

### Task 4: `dyai_crew::review` and `dyai_crew::fix`

**Files:**
- Modify: `scripts/lib/dyai_crew.sh`
- Modify: `scripts/test/dyai_crew.bats`

**Interfaces:**
- Consumes: `get`, `record`, `cmd` (modes `ro` and `rw`), `text`, `failure`,
  `_attempt` from Task 3, and the `reviewer` config.
- Produces:
  - `dyai_crew::review <id> [agent]`. The reviewer defaults to
    `reviewer[<writer>]`. Writes `<state_dir>/<id>.review.md` (the reviewer's
    answer text), prints its path, and records
    `{review, reviewer, verdict, reviewed_sha}`. `verdict` is one of `pass`,
    `fail`, `unknown`. `reviewed_sha` is `git rev-parse crew/<id>` taken
    before the reviewer starts.
  - `dyai_crew::fix <id>`. Runs the writer agent again, in mode `rw`, in the
    same worktree. The prompt holds the original prompt plus the review
    file. It goes through `_attempt`, then records `verdict: null` and
    `reviewed_sha: null`, because the head moved. Refuses unless the verdict
    is `fail`.

Review behaviour: the prompt holds the original prompt, the result summary,
and the diff `git diff <base>..crew/<id>`. A diff up to 100 KiB is inlined. A
larger one is written to `<worktree>/.dyai-review.diff` (personal-ignored),
and the prompt tells the reviewer to read that file: every `ro` mode still
allows reading files. The prompt asks for one JSON object on a line of its
own,
`{"verdict":"pass|fail","findings":[{"path":"","line":0,"severity":"high|medium|low","kind":"defect|plan_drift","problem":""}]}`,
followed by any prose. When the task has a `plan`, the prompt includes it and
asks for a `plan_drift` finding wherever the diff departs from it: files the

### Task 7: `dyai selftest`, proving the policy blocks

**Files:**

**Interfaces:**
- Consumes: `dyai_crew::cmd` from Task 2 and `dyai::enforcement`'s
  `shell rules` column.
- Produces: `dyai_crew::selftest <agent>`. Prints one of `PASS`, `FAIL`,
  `BLOCKED` with a reason. Exit 0 only for `PASS`. `BLOCKED` never counts as
  a pass (Intent Loop result vocabulary). CLI: `dyai selftest [AGENT...]`,
  default every installed agent.

Mechanism (Intent Loop "prove a hook on a call it blocks and on a call it
allows"):
- Add `Bash(dyai-selftest-probe deny *)` to `policy.permissions.deny`. dyai
  translates it into every agent like any other rule.
- `dyai-selftest-probe <deny|allow> <marker-dir>` only writes
  `<marker-dir>/<deny|allow>`. It is harmless whichever way the test goes.
- In a scratch repo, run the agent in mode `rw` with a prompt that asks it to
  run `dyai-selftest-probe allow <dir>`, then `dyai-selftest-probe deny <dir>`.
  `<dir>` is inside the repo, so codex's workspace sandbox can write it.
- The allow flag must admit **both** calls, so that only the deny rule can
  stop the second one. An allow flag scoped to the `allow` call alone would
  make a headless agent refuse the `deny` call anyway, and the test would
  pass with no deny rule at all. Per agent:
  - claude: `--allowedTools "Bash(dyai-selftest-probe:*)"`; deny wins over
    allow.
  - copilot: `--allow-tool "shell(dyai-selftest-probe:*)"`; deny wins over
    allow, but dyai writes no deny rule for copilot (enforcement `-`).
  - codex: `workspace-write` already runs commands; `rules/dyai.rules`
    forbids the deny call.
  - gemini: `--policy <scratch>/allow.toml`, one rule allowing the
    `dyai-selftest-probe` prefix at a priority below the 900 that
    `dyai::permissions_gemini` gives deny rules, so only `policies/dyai.toml`
    can refuse. Not `--approval-mode yolo`: `dyai::setup_gemini` sets
    `security.disableYoloMode`.
  - opencode: the `build` agent already allows `*`; the `permission` block
    dyai writes denies the call.
- The result is compared with the enforcement table, not with "blocked":
  - `allow` marker missing: `BLOCKED: agent ran no command`. This is the
    negative control.
  - The run ends `rate_limited` or `blocked`: `BLOCKED: <reason>`.
  - The table says `M` for the agent's shell rules: `deny` marker absent is
    `PASS`, present is `FAIL: deny rule not enforced`.
  - The table says `S` or `-`: `deny` marker present is
    `PASS: not enforced, as the table says`; absent is
    `FAIL: table says not enforced, but the call was blocked`, which means the
    table is stale.
- It spends quota, so it runs only on demand and never inside `dyai install`.

- Create: `scripts/lib/dyai_zellij.sh`, `scripts/test/dyai_zellij.bats`
- Modify: `scripts/lib/dyai_hunk.sh`, `scripts/test/dyai_hunk.bats`,
  `home/dot_local/bin/executable_dyai-hunk.tmpl` (sources the new library),
  `scripts/test/test_helper.bash` only if a new dybatpho module is needed

**Interfaces:**
- Produces: `dyai_zellij::open <name> <cwd> [keep] -- <cmd...>`. Opens `cmd`
  where the user can see it, and returns 0 when it did:
  1. Inside zellij (`ZELLIJ` set): `zellij run --floating --name <name> --cwd <cwd> [--close-on-exit] -- cmd`.
  2. zellij installed, not inside it: `zellij attach --create-background dyai`,
     then `zellij --session dyai run --name <name> --cwd <cwd> [--close-on-exit] -- cmd`.
     When no client is attached to `dyai` (`zellij --session dyai action list-clients`
     lists none) and kitty remote control is on (`KITTY_LISTEN_ON`), open one
     kitty tab running `zellij attach dyai`, so the pane is on screen.
  3. No zellij, kitty remote control on: a kitty tab running `cmd` (the old
     behaviour, kept as the fallback).
  4. Otherwise return 1; the caller prints the command for the user.
  `--close-on-exit` is passed unless `keep` is given (a log pane stays open
  after the worker ends, so the last lines can be read).

- Used by Task 3 (a pane `crew-<id>` running `dyai logs <id> --follow` for
  each started worker, `keep`) and Task 4 (a pane `review-<id>` running
  `hunk diff <base> crew/<id>` in the task worktree once the review is
  written). Both honour `global.crew.panes`, enum `auto | off`, default
  `auto` (open a pane when `open` can), and never fail the run when no view
  can be opened.
